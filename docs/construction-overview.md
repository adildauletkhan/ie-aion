# IE:AION — Строительная отрасль: техническое описание системы

> Документ-контекст для ИИ. Описывает функционал, модель данных, архитектуру и
> техническую реализацию модуля «Строительство» в платформе IE:AION.

## 1. Общее

**IE:AION** — мультиотраслевая платформа управления производственными активами
(«цифровой двойник предприятия»). Отрасль выбирается из паков (`IndustryPack`):
нефтепровод, газопровод, добыча, энергетика и **строительство**. Каждый пак задаёт
свою навигацию, KPI, иерархию активов и набор модулей.

**Строительный пак** (`src/config/industries/construction.ts`):

- `id`: `construction`, `label`: «Строительство»
- Назначение: управление капитальным строительством — 4D BIM, контроль СМР, план/факт.
- **Иерархия активов:** Холдинг/Застройщик → Проект/Объект → Очередь/Секция → Захватка/Элемент.

## 2. Функционал (модули)

### 2.1 Главная (дашборд)

Сводка портфеля: 4 KPI-карточки (физпрогресс, освоение бюджета, объектов в графике,
LTIFR) со спарклайнами, полоса активных объектов, быстрые действия, плашка отставаний,
оперативная сводка за день, встроенный **ИИ-ассистент** (правая колонка) с поддержкой
рус/каз/англ и выбором источников данных (RAG).

### 2.2 4D-модель (BIM × график)

- Интерактивная **3D-сцена стройплощадки** на Three.js, процедурно генерируемая
  (`src/scene/construction/BuildingScene.tsx`).
- Ползунок **timeline**: состояние каждого BIM-элемента вычисляется по плановому
  прогрессу его задачи на выбранную дату (котлован → сваи → ростверк → цоколь →
  типовые этажи → фасад → кровля).
- Правая панель, реактивная к timeline: индикаторы проекта (план %, факт %,
  активные/отстающие задачи, статус health green/amber/red), S-кривая (план vs факт
  освоения), список активных работ, трудозатраты, материалы.
- Клик по элементу — выделение и карточка деталей.

### 2.3 График и планирование (WBS)

- Иерархия работ **WBS** с фазами, задачами, вехами, зависимостями (FS/SS/FF/SF).
- Переключение вида **Таблица ⇄ Канбан** (4 колонки по статусу).
- В таблице: план (PV), факт (AC), Δ к плану с цветным вариансом.
- Диаграмма Гантта (SVG) с барами по фазам, вехами и связями.
- Ресурсы в отдельных вкладках: подрядчики/субподрядчики, свои силы, спецтехника,
  материалы — с ERP-полями (код номенклатуры, поставщик, план/факт объёмы, покрытие,
  статус поставки).

### 2.4 Смета и бюджет

Бюджет по статьям (`CostItem`), освоение (EV), план/факт затрат, отклонения и варианс.

### 2.5 Контроль СМР (план/факт)

Фактическое выполнение по захваткам (`ZonePlanFact`): план %, факт %, отставание в днях,
статусы.

### 2.6 CV-мониторинг (дрон)

- Список облётов дрона; выбор **VLM-модели** из каталога (аналог Hugging Face).
- Выбор промпт-шаблона (progress / safety / caption / qa / custom) и запуск
  симулированного инференса.
- Результат: сводка, прогресс по захваткам (CV vs план), число распознанных элементов,
  **нарушения ТБ** (без каски/жилета, открытая опасная зона, небезопасные леса, угроза
  падения/подъёма), рекомендации, confidence.
- Превью кадров — **сгенерированная фото-хронология одной площадки** (10 стадий:
  котлован → сдача) из `/public/cv-progression/cv-stage-1..10.png`; кадр выбирается по
  хронологическому рангу облёта. Оверлей bounding-box с подписями объектов (угрозы —
  красным).

### 2.7 Цифровой двойник стройки

Агрегированная панель здоровья проекта (`TwinSummary`): физпрогресс, EV %, SPI, CPI,
отклонение от графика, отстающие захватки, выработка СМР (млн ₸/сут), обеспеченность
материалами, отклонения качества, LTIFR; последние отклонения и прогнозы; навигация
по модулям.

## 3. KPI (10 показателей)

`physical_progress` (%), `earned_value_pct` (%), `spi` (—), `cpi` (—),
`schedule_variance` (дн.), `lagging_zones` (шт.), `daily_smr_value` (млн ₸/сут),
`materials_coverage` (%), `quality_deviations` (шт.), `safety_ltifr` (на 1 млн чел.-ч.).

Методика — **освоенный объём (EVM):** PV (plannedValue), EV (earnedValue),
AC (actualCost); SPI = EV/PV, CPI = EV/AC. Все расчёты — относительно `dataDate` проекта.

Единый источник (пока mock-фикстуры): `src/data/constructionMockData.ts`. Ключевые

| Сущность | Тип | Кол-во (демо) | Назначение |
|---|---|---|---|

| `BimElement` | BIM-элемент | 10 | тип IFC, зона, уровень, bbox, `taskId`, cost |
| `ScheduleTask` | задача графика | 19 | WBS, даты план/факт, PV/EV/AC, status, phaseId, ответственный |
| `Phase` | фаза строительства | 8 | P1…P8, цвет, даты |
| `Resource` | ресурс | 16 | тип (contractor/subcontractor/inhouse/equipment/material), ERP-поля |
| `Milestone` | веха | есть | код, фаза, дата, статус, kind |
| `TaskAssignment` | назначение | есть | task↔resource, объём, lead |
| `TaskDependency` | зависимость | есть | FS/SS/FF/SF, lagDays |
| `CostItem` | статья сметы | есть | код, ед., кол-во, цена, PV, AC |
| `ProgressCurvePoint` | точка S-кривой | есть | дата, PV, EV, AC |
| `ZonePlanFact` | план/факт захватки | есть | план %, факт %, lagDays |
| `Deviation` | отклонение | есть | kind, severity, delta |
| `Forecast` | прогноз | есть | finish_date/cost_at_completion/spi/cpi |

**Демо-проект:** ЖК «Highvill Astana» · 2-я очередь (`proj-highvill-astana`, код HVA-2026),

**Захватки (8):** БС-1 фундамент / этажи 1-6 / этажи 7-12; БС-2 фундамент / этажи 1-6 /
этажи 7-12; Паркинг подземный; Благоустройство.

**Фазы (8):** P1 Подготовка площадки, P2 Нулевой цикл, P3 Монолит надземной части,
P4 Фасад и кровля, P5 Инженерные сети (ОВиК/ВК/ЭОМ/СС), P6 Отделка, P7 Благоустройство,

## 5. API-поверхность (data layer)

Все fetch-функции возвращают `Promise` с имитацией сетевой задержки, сигнатуры совместимы
с будущими REST-эндпойнтами `/api/construction/projects/{id}/...` — свап на реальный
бэкенд без правок UI:

`getCurrentProjectId`, `fetchProject`, `fetchElements`, `fetchTasks`, `fetchCostItems`,
`fetchProgressCurve`, `fetchZonePlanFact`, `fetchDeviations`, `fetchForecasts`,
`fetchTwinSummary`, `fetchPhases`, `fetchResources`, `fetchMilestones`, `fetchAssignments`,
`fetchDependencies`, `fetchCvModels`, `fetchDroneFlights`, `fetchCvAnalysisRuns`.

Данные кэшируются через `@tanstack/react-query`.

## 6. Интеграции (10)

BIM/CAD: **Autodesk BIM 360 / ACC, Autodesk Navisworks, Trimble Tekla Structures,
СОД/CDE**. Графики: **Oracle Primavera P6, Microsoft Project**. ERP/учёт: **1С:ERP,
1С:УПП, 1С:Бухгалтерия, SAP PS**.

Модуль «Интеграции» — industry-aware: подтягивает список из пака и показывает **маппинг
полей** (`mappingEntities`) с внешними именами полей и трансформациями
(Direct/Map/Date/Custom) под каждую систему. Источник ресурса фиксируется в данных
(`Resource.erpSource`: erp_1c / upp_1c / buh_1c / sap_ps / manual).

## 7. Архитектура

### 7.1 Frontend

- **React 18 + TypeScript**, сборка **Vite 5**.
- UI: **Tailwind CSS + shadcn/ui** (Radix), иконки **lucide-react**, тосты **sonner**.
- Роутинг: **react-router-dom**; данные: **@tanstack/react-query**.
- 3D: **Three.js** через **@react-three/fiber** + **@react-three/drei** (сцена
  стройплощадки, 4D по timeline).
- Графики: **Recharts**; таблицы/Канбан/Гантт — собственные компоненты (Гантт на SVG).
- Аутентификация: Basic Auth, учётные данные в `localStorage`.

### 7.2 Backend

- **FastAPI (Python 3.13)**, **PostgreSQL**, **SQLAlchemy**, миграции **Alembic**.
- Обслуживает: аутентификацию (`/api/me`), администрирование пользователей,
  **ИИ-ассистента** (`/api/ai/chat`, LLM GPT-4o-mini через OpenAI), общие доменные данные.
- **Важно:** строительный домен на текущем этапе работает на **frontend mock-данных**
  (`constructionMockData.ts`); отдельные строительные таблицы/эндпойнты в бэкенде ещё
  не заведены — data layer спроектирован под будущий свап на REST.

### 7.3 Развёртывание

- **Docker / Docker Compose** (Postgres), облако **Railway**; `Dockerfile.backend`,
  `Dockerfile.frontend`.
- Локально: БД Postgres в docker (`aion-db`, порт `5438`), бэкенд uvicorn (`:8002`),
  фронтенд Vite (`:8080`); Vite проксирует `/api` → `:8002`.

## 8. Техническая реализация 3D (детали)

- `ConstructionScene` строит 2 корпуса (БС-1/БС-2), подземный паркинг, башенный кран,
  бытовку, забор, котлован, свайное поле — процедурно по прогрессу задач.
- Устранён z-fighting: `logarithmicDepthBuffer`, явные near/far камеры, разнесение
  co-planar граней (окна/рамы/стены/плиты/колонны), `depthWrite=false` для прозрачных
  стёкол.
- Логика этажности: верхний стек этажей не отображается, пока физически не достроен
  нижний (нет «парящих» этажей).

## 9. Цветовая/UX-система

Единый брендовый акцент (бирюза) + семантика статусов: зелёный = в графике/ок,
янтарь = отставание/внимание, красный = критично; остальное нейтральное. Дашборд
оптимизирован по объёму информации; декоративная многоцветность иконок/категорий убрана
в пользу нейтральных.
