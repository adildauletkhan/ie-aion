# ТЗ: Бригадиры, детальный план проекта, суточный журнал и динамика — IE:AION

> Расширяет строительный пак платформы IE:AION (см. `construction-overview.md`) и
> связывает его с Telegram-ботом (`bot.py`, `voice-report-system-prompt.md`,
> `telegram-bot-tech-spec.md`). Закрывает разрыв: сейчас бот не видит реальные объекты
> и бригадиров, потому что в IE:AION нет ни модуля бригадиров, ни backend API для
> строительного домена (только mock-данные во фронтенде).

---

## 0. Проблема и цель

**Сейчас**: бот работает с захардкоженным списком объектов (`PROJECTS` в `bot.py`),
не знает реальных бригадиров, не видит реальный WBS объекта, и некуда записывать
подтверждённые отчёты — в IE:AION строительный домен живёт только на фронтенде
(`constructionMockData.ts`), backend для него не заведён.

**Нужно построить 4 связанных куска**:

1. **Модуль «Бригадиры»** в IE:AION — реестр бригадиров/прорабов, привязка к
   Telegram, к объекту и к конкретной бригаде/подрядчику
2. **Детальный план проекта (WBS)** — сделать существующий модуль «График и
   планирование» единственным источником правды для бота (сейчас там mock, 19 задач)
   плюс расширить визуализации
3. **Суточный журнал** — новый модуль, который накапливает подтверждённые отчёты
   (голосовые из бота + ручной ввод в самом IE:AION) в разрезе дня/объекта/захватки
4. **Динамика проекта** — дашборд, показывающий изменение показателей во времени
   (то, что уже частично есть как `TwinSummary` и S-кривая, но нужно наполнить
   реальными данными из суточного журнала, а не статичным mock)

### 1.2 UI в IE:AION

Новый пункт навигации в строительном паке: **«Бригадиры»** (`/construction-crews`),
рядом с «Контроль СМР».

- Таблица: ФИО, роль, бригада/подрядчик, объект, зона по умолчанию, статус Telegram
  (не приглашён / приглашение отправлено / привязан), последний отчёт (дата)
- Действие «Пригласить» — генерирует `invite_code`, показывает ссылку вида
  `t.me/tanra_report_bot?start=INV-XXXXXX` (deep link с параметром) для отправки
  бригадиру любым удобным способом (WhatsApp, SMS, устно)
- Карточка бригадира — история его отчётов (ссылка на суточный журнал,
  отфильтрованный по нему)

### 1.3 Привязка Telegram (изменение в bot.py)

Сейчас `/start` в боте не проверяет, кто пишет. Меняем логику:

```
/start INV-XXXXXX  →  бот ищет Foreman по invite_code
                       если найден и telegram_link_status != linked:
                           записывает telegram_user_id, статус → linked
                           дальше бот уже знает project_id и default_zone
                           этого бригадира — не нужно спрашивать /object
/start (без кода)  →  если telegram_user_id уже привязан к Foreman — работает как раньше
                       если не привязан — просит код приглашения от ПТО/PM,
                       НЕ даёт доступа к произвольному выбору объекта
```

Это закрывает и вопрос безопасности из ТЗ бота (§8) — доступ только по регистрации,
не открытый для всех.

## 2. Детальный план проекта (WBS) — источник правды для бота

### 2.1 Что уже есть (по `construction-overview.md`)

Модуль «График и планирование» уже поддерживает: иерархию WBS с фазами/задачами/
вехами/зависимостями, таблицу с план/факт/варианс, канбан (4 колонки по статусу),
диаграмму Гантта (SVG), ресурсы по вкладкам. Всё это пока на mock (`ScheduleTask` × 19).

### 2.2 Что нужно добавить

1. **Backend-эндпоинт для бота**: `GET /api/construction/projects/{id}/active-tasks`
   — возвращает задачи в статусе `in_progress`/`planned` на дату, отформатированные
   ровно под схему `active_wbs_tasks` из `voice-report-system-prompt.md` (§2):
   `task_id, wbs_code, name, zone, phase_id, planned_progress_pct, status,
   responsible`. Именно этот эндпоинт бот дергает перед вызовом LLM-структурирования,
   вместо захардкоженного списка.
2. **Доп. визуализация — S-кривая по захваткам**: сейчас S-кривая (план vs факт
   освоения) есть только на уровне всего проекта (в 4D-модуле). Добавить разрез по
   захватке/зоне — понадобится для «динамики» в разделе 4.
3. **Привязка задачи к зоне бригадира**: убедиться, что у каждой `ScheduleTask` есть
   `zone`, совпадающая по формату с тем, что бригадиры реально говорят голосом
   (см. matching logic в промпте бота, §4) — иначе `unmatched` будет массовым.

## 3. Суточный журнал (новый модуль)

### 3.1 Назначение

Единая лента событий по объекту за день: и то, что прислали через бота (голос+фото),
и то, что ПТО/PM внесли вручную прямо в IE:AION (для случаев без Telegram, или для
корректировок).

### 3.2 Сущность `DailyJournalEntry`

| Поле | Тип | Описание |
|---|---|---|
| `entry_id` | uuid | |
| `project_id` | string | |
| `date` | date | |
| `zone` | string | |
| `task_id` | string \| null | FK на `ScheduleTask`, null если `unmatched` |
| `work_type` | string | |
| `plan_pct` | float | из `ScheduleTask` на момент записи |
| `fact_pct` | float | |
| `delta_pct` | float | |
| `source` | enum | `voice` / `manual` / `cv` (на будущее — дрон/CV) |
| `author_foreman_id` | uuid \| null | если source = voice, кто прислал |
| `author_user_id` | uuid \| null | если source = manual, кто из ПТО/PM внёс |
| `blocker_type` | enum \| null | resource / dependency / external / quality / none |
| `blocker_description` | string \| null | |
| `risk_delay_days` | int \| null | |
| `risk_severity` | enum \| null | risk / attention / critical / none |
| `responsible` | string \| null | |
| `actions` | string[] | рекомендованные действия |
| `raw_transcript` | text \| null | для source = voice |
| `photos` | string[] | ссылки на медиа |
| `confirmed` | boolean | |
| `created_at` | timestamp | |

Это, по сути, персистентная форма `structured_data.entries[]` из промпта бота
(§5.1) — журнал и есть накопитель того, что бот генерирует, плюс ручных записей.

### 3.3 UI в IE:AION

Новый пункт навигации: **«Суточный журнал»** (`/construction-journal`).

- **Вид по умолчанию** — лента по дням (последний день сверху), внутри дня —
  группировка по захваткам, каждая запись показывает то же самое, что видит
  бригадир в Telegram-черновике (зона, работа, факт%, причина, риск, действие,
  источник — иконка голоса/ручного ввода/CV)
- **Фильтры**: по объекту, по захватке, по бригадиру/подрядчику, по периоду,
  по наличию риска/отклонения
- **Ручное добавление записи** — кнопка «Добавить запись» открывает форму с теми же
  полями, что и `DailyJournalEntry` — для случаев, когда бригадир недоступен в
  Telegram или ПТО вносит корректировку по итогам обхода
- **Редактирование** — запись, пришедшую от бота, ПТО может поправить (это тоже
  создаёт запись в истории изменений — не перезаписывает молча)

### 3.4 Связь с ботом

Хендлер подтверждения отчёта в `bot.py` (`on_confirm`, сейчас с `TODO`) вызывает:

```
POST /api/construction/projects/{id}/journal
Body: structured_data.entries[] (из voice-report-system-prompt.md, §5.1)
      + author_foreman_id (из Foreman, найденного по telegram_user_id)
```

Backend при получении:
1. Создаёт `DailyJournalEntry` на каждый `entry`
2. Обновляет `ScheduleTask.actualProgressPct` для найденного `task_id`
3. Обновляет/создаёт `ZonePlanFact` по захватке
4. Если `delta_pct` существенно отрицательный или есть активный `blocker` —
   создаёт `Deviation`

## 4. Динамика проекта («как было задумано»)

### 4.1 Что уже задумано в платформе

По `construction-overview.md`, §2.7 — модуль **«Цифровой двойник стройки»** уже
должен показывать: физпрогресс, EV%, SPI, CPI, отклонение от графика, отстающие
захватки, выработку СМР, обеспеченность материалами, отклонения качества, LTIFR,
**последние отклонения и прогнозы**. Плюс в §2.2 (4D-модель) есть S-кривая план vs
факт.

**Проблема сейчас**: все эти цифры считаются от статичного mock (`ProgressCurvePoint`,
`Forecast` — фиксированные демо-значения), а не от реально накапливающихся данных.

### 4.2 Что нужно сделать

1. **Ежедневный пересчёт**: при каждой новой записи в `DailyJournalEntry` —
   пересчитывать `ZonePlanFact` → агрегировать в `ProgressCurvePoint` на эту дату
   (EV/PV/AC по проекту на сегодня) → это и есть реальная точка на S-кривой вместо
   статичной демо-точки.
2. **Историчность**: `ProgressCurvePoint` уже спроектирована как временной ряд (дата,
   PV, EV, AC) — просто нужно, чтобы она реально пополнялась, а не была захардкожена.
   Тогда S-кривая в 4D-модуле и график динамики в цифровом двойнике начнут расти
   день за днём по мере поступления отчётов бригадиров.
3. **Тренд отклонений**: добавить на дашборд «Цифровой двойник» график
   «Deviations over time» — сколько новых `Deviation` появилось за последние N дней,
   сколько закрыто — это прямой показатель того, работает ли контроль исполнения.
4. **Разрез по источнику данных**: на дашборде показывать долю записей `voice` vs
   `manual` vs `cv` за период — метрика полезности бота (насколько бригадиры реально
   им пользуются вместо ручной отчётности ПТО).

### 4.3 Визуализация

- Существующая S-кривая (Recharts) — доработать, чтобы тянуть реальные
  `ProgressCurvePoint` из backend, а не mock
- Новый мини-виджет на дашборде «Главная»: спарклайн «физпрогресс за 14 дней» —
  вместо статичного значения показывает тренд
- В «Цифровом двойнике» — таймлайн отклонений (список `Deviation` с датой
  возникновения и, если есть, датой закрытия)
